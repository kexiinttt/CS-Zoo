# What is ABI

ABI is **Application Binary Interface**, which is the "Application Binary Interface". It solves the problem of "whether different modules can be connected and run correctly after being compiled into a binary."

ABI is "how the compiler and linker ultimately agree that these codes will cooperate at the machine level."

The ABI focuses not on what the function name looks like on the surface, but on the lower-level binary conventions, such as:
- How to pass function parameters
- How to pass the return value
- How to modify symbol names (name mangling)
- The layout of class objects in memory
- How to organize the virtual function table
- How exceptions propagate across modules
- Are the binaries generated by different compilers/standard libraries compatible?

---

# Why ABI is important

## Dynamic library/static library compatibility

You write a `.so` / `.dll` / `.a`. When others use it to link, in addition to the header file being compiled and passed, you must also ensure that the conventions at the binary level are consistent, otherwise it may be:

- Link failed
- Crash during runtime
- Object layout is disordered
- delete/free wrong object
- Exception cross-border problems

## Compiler Compatibility

The same C++ source code, different compilers may:

- mangling rules are different
- Class layout details are different
- RTTI / exception implementation is different
- Standard library implementation is different

Therefore, although many C++ libraries have "the same API", they are not necessarily ABI compatible.

## Version upgrade compatibility

After a library is upgraded, even if the source code interface has not changed much, as long as the object layout or symbols are changed, the ABI may be damaged, making the old program unable to directly replace the new library.

- ABI stability
- backward binary compatibility

# What does ABI include?

## Calling Convention (calling convention)

Conventions are required when calling functions:

- Should the parameters be placed in registers or on the stack?
- Who is responsible for cleaning the stack
- Where to put the return value?
- How to pass this pointer

Even if the source code looks the same, the underlying calling convention may be different.

## Name Mangling (name modification)

C++ supports:

- Function overloading
- namespace
- Class member functions
- template

Therefore, the compiler cannot just retain the original function name in the source code, but must encode the type information into the symbol.

For example:

```cpp
void func(int);
void func(double);
```

After compilation, they will not all be called `func`, but different mangled names.

This brings two consequences:

1. The mangling rules of different compilers may be different.
2. C++ symbols are generally not suitable as stable cross-compiler ABIs

Therefore, many binary interfaces exposed to the outside world will use:

```cpp
extern "C"
```

to turn off C++ name mangling, making exported symbols more stable.

## Object Layout (Object Layout)

How classes are arranged in memory is also part of the ABI, for example:

- Member variable order
- padding/alignment
- base class placement
- Where to put vptr
- multiple inheritance layout
- virtual inheritance layout

```cpp
struct A {
    int x;
    char y;
};
```

Its `sizeof(A)` is often not 5, but maybe 8 because of alignment and padding.

If the library version is upgraded, change it to:

```cpp
struct A {
    char y;
    int x;
};
```

At the source code level, it looks like the order has just been changed, but the ABI has changed because the memory layout has changed.

## Virtual Table / RTTI

Classes with virtual functions generally have:

- vptr
- vtable
- RTTI information

These implementation details are also typically subject to the ABI.

For example:

```cpp
struct Base {
    virtual void f();
    virtual ~Base() = default;
};
```

There is usually an additional hidden pointer in the object pointing to the vtable.  
If you change the order of virtual functions, add/remove virtual functions, the vtable layout may change, breaking the ABI.

## Exception Handling

When exceptions are propagated across modules, they depend on:

- Stack expansion mechanism
- type info
- runtime support
- Exception implementation in standard library/compiler

> Don't let C++ exceptions propagate across dynamic library boundaries easily, especially if compilers, standard libraries, or compilation options are not uniform.

## ABI of standard library types

Like these types:

- `std::string`
- `std::vector`
- `std::list`
- `std::function`

Their internal implementation details are not mandated by the language standard, but are determined by the standard library implementation.  
Therefore, the ABI may be different between different versions of libstdc++ / libc++ / MSVC STL.

# OpaqueHandle

Many large-scale C++ projects will use C++ internally and export C interfaces externally. The reason is that C's ABI is usually simpler and more stable:

- No function overloading
- No name mangling (or the rules are simpler)
- No class object layout compatibility issues
- No template instantiation ABI issue
- More suitable for cross-language calls

Typical writing:

```cpp
extern "C" {
    void* create_handle();
    void destroy_handle(void* p);
}
```

But it doesn't solve:

- Calling convention differences
- Object layout differences
- Differences in abnormal mechanisms
- allocator/runtime differences
- STL/RTTI/vtable issues

# What changes are likely to break the ABI?

* Modify class member variables
    - Add new members
    - Delete members
    - Adjust the order
    - Change type
    - Changing access control usually does not affect the ABI, but changing the layout will.

* Modify virtual function table
    - Add virtual function
    - Remove virtual functions
    - Adjust virtual function declaration order
    - Modify virtual inheritance structure

* Modify function signature
    - Parameter type changes
    - Return type changes
    - `noexcept` changes may also affect interface conventions/symbols in some scenarios
    - Changing the default parameters itself is usually an API problem, not directly an ABI problem, because the default parameters are expanded at the call point

* Change the way template instances are exposed
* Expose STL members or return STL types

# Relationship with template / inline

The implementation of template / inline is written in the header. Once the user compiles, he will instantiate / compile these implementations into his own binary. This means that even if the dynamic library is replaced, the running code compiled by the user still uses the old logic.

> It is equivalent to ordinary functions that use the one in the dynamic library every time they are called; templates and inlines "copy and paste" the code when compiling, and there is no need to search for the dynamic library when calling, so as long as they are not recompiled, the old ones will always be used, no matter how the dynamic library changes.


## Why template is not ABI friendly

Ordinary function libraries are like "finished machines" (.so). If you change to a new machine, the old program can still be used. The template is more like a "drawing" (in the header file), and the user builds the machine on site.

So after you change the drawing (template implementation):
- If the user does not recompile, he or she will still have an old machine.
- After recompiling, the internal details of the machine may have changed.
- Different factories (compilers/standard libraries) may produce different products.

## Why is inline not ABI friendly?

`inline` functions are often defined in header files. The caller may compile the function body directly into its own binary.

So even if you replace the dynamic library, if the caller does not recompile, the old inline logic will still be there.

# PImpl (Pointer to Implementation)

```cpp
// widget.h
class Widget {
public:
    Widget();
    ~Widget();

    void doWork();

private:
    struct Impl;
    std::unique_ptr<Impl> impl_;
};
```


```cpp
// widget.cpp
struct Widget::Impl {
    int x;
    std::string name;

    void doWorkImpl() {
        // real logic
    }
};

Widget::Widget() : impl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;

void Widget::doWork() {
    impl_->doWorkImpl();
}
```

What the user sees is the Widget, and they cannot see what members and implementations are in Impl. In this way, the user can get a very stable public interface. It is equivalent to isolating "easy-to-change implementation" behind the ABI boundary.
